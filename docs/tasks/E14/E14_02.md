# E14_02 - Core: boot ROM mapping in the bus
Role: CODE
Goal: The bus can overlay a boot ROM that disappears on a write to $FF50.
Prerequisites: E14_01
Read (max 3 files, give line ranges): crates/puce8gb-core/src/bus.rs (grep first: fn read, fn peek, FF50, IO_SIZE); docs/annexes/notes/10_boot_rom.md; docs/annexes/decisions.md (A_11)
Write only in: crates/puce8gb-core/src/bus.rs, crates/puce8gb-core/src/bus/
## Work
1. Bus gets a boot ROM slot: `boot_rom: Option<Box<[u8]>>` and `boot_mapped: bool` (false by default).
2. `pub fn set_boot_rom(&mut self, data: &[u8], expected_len: usize) -> Result<(), BootRomError>` with `pub enum BootRomError { BadSize }` (new, in the same module as the bus). Installing a valid ROM sets boot_mapped = true.
3. While boot_mapped, a read (and peek) of $0000..=$00FF returns the boot ROM byte (only that range at this stage; the CGB range $0200..=$08FF is added later by E15). Everything else is unchanged.
4. A write to $FF50 with a non-zero value sets boot_mapped = false. A write of 0 changes nothing. Once unmapped the ROM only comes back with `Bus::remap_boot()` (called by reset, added in E14_03). Reading $FF50 keeps its present behaviour.
5. Tests with a synthetic 256-byte boot ROM filled with $C3 and a cartridge whose byte 0 is $AA: read($0000) = $C3 while mapped and read($0100) is the cartridge byte; after write($FF50,1) read($0000) = $AA; write($FF50,0) after that changes nothing; set_boot_rom with 255 bytes and expected_len 256 gives Err(BadSize) and leaves boot_mapped false; the e09_02 bus layout tests still pass unchanged (the new fields are not saved yet).
